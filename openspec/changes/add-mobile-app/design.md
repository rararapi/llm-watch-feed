## Context

現行プロダクトは Python製のSSG。フロントは Vanilla HTML/JS/CSS（FW不使用が設計ルール）で、`templates/` + `assets/site/` を `generate_pages.py` が生成する。記事データ `models.json`（最大500件・約73KB）は公開GCSバケットの `data/models.json` からHTTPS＋CORS設定済みで配信され、すでに「読み取り専用API」として成立している。RSS・AI生成画像も同バケットから配信。

このため、モバイルアプリ追加にあたっての制約・前提は以下:

- Web側にReact等のUI資産が無く、**UIコードの再利用は不可能**。再利用できるのは「データ契約・表示定数・小さなビジネスロジック（絞り込み/日付グルーピング/サムネ優先順）」。
- 既存Web・収集パイプライン・配信構成は無改修で稼働継続させる（モバイルは純粋な追加）。
- APIキー・機密はフロント／公開ディレクトリに出さない既存方針を厳守する。アプリは読み取り専用で認証情報を持たない。

## Goals / Non-Goals

**Goals:**
- 公開 `models.json` を直接消費し、Web機能パリティ（一覧・絞り込み・詳細）を満たす iOS/Android アプリを **バックエンド改修ほぼゼロ** で提供する。
- データスキーマと表示定数の「単一の真実」を保ち、Web/アプリ間のドリフトを防ぐ。
- 既存Webの稼働・配信に一切影響を与えない。

**Non-Goals:**
- Push通知（Phase 2・別提案。バックエンドにトークン保管と送信処理が必要）。
- `models.json` のスキーマ変更・命名一般化。
- アプリ専用APIサーバ/BFFの新設、ブックマークのクラウド同期、課金/アフィリエイトのストア対応。
- 既存SSG/RSSのリプレース。

## Decisions

### D1. Expo (managed workflow) を採用（bare RN ではなく）
- **理由**: コンテンツフィード型の読み取りアプリにネイティブモジュールの自作はほぼ不要。EAS Build（ストア配布）/ EAS Update（JS OTA）/ Expo Push（Phase 2）が揃い、iOS/Android最短で到達できる。
- **トレードオフ**: 一部ネイティブ機能はExpoの提供範囲に依存。将来必要になれば config plugin / prebuild で bare へ移行可能なため、初期の制約リスクは低い。
- **代替案**: bare React Native（自由度は高いがビルド/CI/署名の運用コストが大きく、本アプリの要件に対し過剰）。

### D2. リポジトリはモノレポ・main管理（`app/` を追加）
- **理由**: 最も同期させたいデータスキーマ・表示定数を、それを生成する Python（`generate_pages.py`）の隣に置ける。スキーマ変更とアプリ追従を原子的にコミットできる。小規模・単一プロダクトでマルチリポの整合コストが見合わない。
- **トレードオフ**: Python リポに Node/Expo ツールチェーン（node_modules/EAS）が同居する。→ `.gitignore` と CI のパスフィルタで分離し、ノイズと相互干渉を抑える。将来モバイルが独立チーム/リリースになれば `git filter-repo` で履歴ごと分離可能。
- **代替案**: 別リポ（独立リリース・権限分離に有利だがスキーマ同期が手作業に）/ ブランチ分離（長命ブランチのドリフトで却下）。

### D3. データ取得は公開 `models.json` を直接fetch（BFFを作らない）
- **理由**: 既にCORS対応の公開JSONがあり、v1で追加のサーバは不要。`TanStack Query` でfetch＋キャッシュ、`MMKV`（または AsyncStorage）でオフライン永続化する。
- **トレードオフ**: ページングが無く全件（最大500件・約73KB）取得。現状の規模では問題ないが、増大時はバックエンドにモバイル向け軽量/分割JSONを追加する余地を残す（別提案）。
- **代替案**: 専用API/BFF（v1には過剰）。

### D4. スキーマと表示定数の単一ソース化
- **理由**: `Article` 型はTSで一度だけ定義しアプリ全体の型の真実とする。ソース/色/ラベル等のPython由来定数は `generate_pages.py` が `shared/meta.json` を**追加出力**し、アプリはこれを参照（ビルド時取り込み可）。Web/アプリのドリフトを防ぐ。
- **トレードオフ**: `generate_pages.py` に出力処理が1つ増える。既存サイト出力には非干渉（純粋な追加）で、失敗してもサイト生成は完走させる。
- **代替案**: アプリ側に定数をハードコード（ドリフト不可避で却下）。

### D5. 記事詳細はネイティブ描画＋アプリ内ブラウザで元記事
- **理由**: 要約/impact/action をネイティブ表示するのが最もアプリらしいUX。元記事は `expo-web-browser` のアプリ内ブラウザで開き離脱を抑える。
- **トレードオフ**: 既存SSGの記事ページ（OGP焼き込み済みHTML）をWebViewで丸ごと再利用する案より実装は増えるが、UX・パフォーマンスで上回る。
- **代替案**: 記事ページをWebView表示（Web資産を最大再利用できるがアプリ感が薄い）。

### D6. ナビゲーション/ライブラリ
- `expo-router`（ファイルベース・ディープリンク容易）、`TanStack Query`（取得/キャッシュ/再試行）、`MMKV`（高速ローカル永続化）、`expo-web-browser`（アプリ内ブラウザ）、`expo-sharing`/標準Share（共有）。外部依存はアプリの中核要件に必要なものに限定する。

### D7. CI/CD はパスフィルタで分離
- **理由**: 既存 `deploy.yml`（日次ジョブ/サイト）と干渉させない。アプリ用ワークフローは `app/**` 変更時のみ EAS Build/Update を実行。
- **トレードオフ**: ワークフローが1本増えるが、責務が明確に分かれる。

## Risks / Trade-offs

- **[全件取得が将来肥大化] models.json が大きくなると初回ロードが重くなる** → 当面は500件上限で十分軽量。閾値を超えたらモバイル向け軽量/分割JSONをバックエンドに追加（別提案）。
- **[スキーマのドリフト] Python側のフィールド変更にアプリTS型が追従漏れ** → `shared/meta.json` と `Article` 型を単一ソース化し、スキーマ変更時はモノレポ内で同一PRに追従を含める運用とする。
- **[Expoの制約] 将来ネイティブ要件が増える** → config plugin/prebuild で対応、最終手段は bare 移行（D1の通り低リスク）。
- **[ストア審査] アフィリエイト/外部リンクの扱い** → v1は閲覧専用でアフィリエイトをアプリに持ち込まない。収益化時に審査ポリシーを別途確認。
- **[CORS/配信変更] 将来バケットのCORSやURLが変わるとアプリが壊れる** → 配信URL・CORSは設定済み。変更時はモノレポ内で `shared/meta.json` 経由のベースURL共有等で一元管理する余地を残す。

## Migration Plan

純粋な追加機能のため既存システムのマイグレーションは不要。

1. `generate_pages.py` に `shared/meta.json` 出力を追加（既存出力に非干渉。失敗してもサイト生成は完走）。
2. `app/` に Expo プロジェクトを作成し、`models.json` 消費の一覧/詳細/絞り込み/オフラインを実装。
3. EAS Build で内部配布（TestFlight / Play内部テスト）。
4. ロールバック: アプリは独立成果物のため、問題時はストア/EAS Updateのロールバックのみ。既存Web・配信は影響を受けない。`shared/meta.json` 出力の取り消しはサイト生成に影響しない。
